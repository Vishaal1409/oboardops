## 1. Checklist Generator — `tools/checklist_tool.py`

### `generate_checklist(role: str, department: str) -> str`

**Input**
- `role` — job title, e.g. `"Software Engineer"`. Required, non-blank after `.strip()`.
- `department` — department name, e.g. `"Engineering"`. Required, non-blank after `.strip()`.

**Output**
- Success: a Markdown string —
  ```
  ### Onboarding Checklist: <role> (<department>)

  - <item 1>
  - <item 2>
  ...
  ```
  Always 5–7 bullet items (enforced by an internal Pydantic model, `min_length=5, max_length=7`), each a single actionable step starting with a verb.
- Failure: `"Error: <field> is required and cannot be empty."` (blank/whitespace-only `role` or `department`) or `"Unexpected error: <exception>"` (any other failure — e.g. Bedrock throttling, network error, malformed model output).

**How it generates the output**: builds a `strands.Agent` backed by `BedrockModel` (`model_id="us.anthropic.claude-sonnet-4-6"`, this AWS account's confirmed-accessible Claude model — `claude-opus-5`/`claude-sonnet-5` are not yet enabled on this account), with a system prompt that (a) forbids generic filler items and (b) injects the full text of `.claude/skills/indian-hr-compliance/SKILL.md` so statutory items (PF, ESI, POSH, gratuity, appointment letters) cite real forms/thresholds instead of model recall. If that skill file is missing, the tool logs a warning and falls back to generating without the compliance reference rather than failing.

**Dependencies**: valid AWS credentials with Bedrock `Converse`/`ConverseStream` access to `us.anthropic.claude-sonnet-4-6` in the configured region; `pydantic`, `strands-agents`, `boto3`.

**Verified behavior** (from prior stress testing, 50 role/department combinations + edge cases): correctly disambiguates ambiguous titles by department context (e.g. `"MD"` → Managing Director under `"Executive"`, Medical Doctor under `"Healthcare"`); correctly reasons about employment-type nuance (e.g. `"Freelance Contractor"` gets TDS 194C/194J guidance instead of salaried TDS); redundant-sounding role/department pairs (`"HR"/"Human Resources"`) don't produce degenerate output. One observed latency outlier reached 195s under concurrent load — no client-side timeout is currently enforced around the Bedrock call. Re-confirmed through the *full agent* (not just the standalone function) on 2026-09-06: "Intern, Legal", blank-department (agent asks a clarifying question instead of calling the tool), and "MD, Healthcare" (still disambiguates correctly) — see `e2e/test_agent_full_integration.py`.

### `parse_checklist_items(markdown: str) -> list[str]`

**Input**: a `generate_checklist()` Markdown string (or any string).
**Output**: the raw item sentences, in order, with the leading `"- "` stripped. Returns `[]` for input with no `"- "`-prefixed lines (e.g. an `"Error: ..."` string) rather than raising.

### `short_task_label(item_text: str, max_len: int = 60) -> str`

**Input**: one checklist item sentence; optional `max_len` (default 60).
**Output**: a short, deterministic label — cuts at the first clause-boundary separator (em dash `—`, en dash `–`, `: `, or `; `) if one exists past character 10, else hard-truncates at a word boundary and appends `…`. Added 2026-09-06 to bridge `generate_checklist` output into `tracker_tool.py`'s `Task` column (previously untested — see `KNOWN_ISSUES.md` #3); **not** exposed as an `@tool` (the fix reaches the agent instead via updated docstrings on `log_status`/`update_task_status`). Does not solve `generate_checklist`'s non-determinism across calls — a label from one generation can't be used to reference a later regeneration.

## 2. HR Policy Q&A — `tools/hr_qa_tool.py` (+ `tools/hr_qa_wrapper.py`)

> **Two implementations of the same tool currently coexist** — see [Gaps](#gaps--inconsistencies) below.

### `HRQATool` class (`tools/hr_qa_tool.py`)

- **Constructor**: `HRQATool(knowledge_base_path: Path | str = PROJECT_ROOT / "hr_qa_knowledge_base.json")`. Raises `FileNotFoundError` if the file doesn't exist, `ValueError` if it's invalid JSON or lacks a top-level `hr_policies` list.
- **`.search(question: str, threshold: float = 0.4) -> dict | None`** — fuzzy-matches `question` against every policy's `question` field (`difflib.SequenceMatcher` similarity + a keyword-overlap boost up to `+0.15`), returns the best match above `threshold` as `{"question", "answer", "category", "priority", "confidence"}`, or `None` if nothing clears the threshold.
- **`.search_by_category(category: str) -> list[dict]`** — all policies whose `category` matches (case-insensitive), each as `{"question", "answer", "category", "priority"}`; `[]` if none match or `category` is blank.
- **`.get_all_categories() -> list[str]`** — sorted list of distinct category strings present in the knowledge base.
- **`.answer_question(question: str) -> str`** — the tool-facing entry point: returns the matched answer, with `"\n\n[Confidence: NN%. Verify with HR if needed.]"` appended when confidence `< 0.6`; returns `"I couldn't find an answer to that question. Please contact HR at hr@company.com."` when nothing matches.

### `@tool answer_hr_question(question: str) -> str` (module-level, `tools/hr_qa_tool.py`)

**Input**: `question` — free-text employee question, e.g. `"How many paid leave days do I get?"`. No validation on blank input (an empty string just fails to match and falls through to the "couldn't find" response).

**Output**: plain-text answer string, confidence caveat, or fallback message (see `.answer_question` above). Wrapped in try/except: `FileNotFoundError` → `"Setup Error: ..."`; `ValueError` → `"Configuration Error: ..."`; anything else → `"Unexpected error: ..."`.

### `@tool list_hr_policy_categories() -> str`

**Input**: none.
**Output**: `"Available HR policy categories: benefits, compensation, employment_terms, leave_policy, policies, reimbursement, work_arrangements"` (comma-joined, sorted), or `"No HR policy categories found."` if the knowledge base is empty.

### `@tool answer_hr_question(question: str) -> str` (`tools/hr_qa_wrapper.py` — the one actually wired into `agent.py`)

Same signature and output shape as above, but backed by its own module-level `HRQATool` instance created eagerly at import time with a **relative** path (`knowledge_base_path="hr_qa_knowledge_base.json"`), not `PROJECT_ROOT`-based — this only resolves correctly if the process's working directory is the repo root.

### Knowledge base schema — `hr_qa_knowledge_base.json`

```json
{
  "hr_policies": [
    {
      "question": "How many paid leave days do I get per year?",
      "answer": "Full-time employees get 21 paid leave days (PL) annually. ...",
      "category": "leave_policy",
      "priority": "high"
    }
  ]
}
```
Currently 10 policies across 7 categories: `leave_policy`, `employment_terms`, `reimbursement`, `benefits`, `work_arrangements`, `policies`, `compensation`.

**Verified behavior** (`test_hr_qa_stress.py`, 10 paraphrased/casual questions like `"can i work from my couch?"` and `"maternity leave for men?"`): fuzzy matching handles informal phrasing above the tool's own `0.5` pass bar.

## 3. First-Week Schedule — `tools/scheduling_tool.py`

### `generate_schedule(start_date: str) -> list`

**Input**: `start_date` — employee start date as `"YYYY-MM-DD"`.

**Output**: a list of exactly 5 dicts, one per working day of the onboarding week:
```json
{
  "date": "2026-08-31",
  "weekday": "Monday",
  "day": "Day 1",
  "title": "Welcome & Setup",
  "meetings": [
    "Welcome and HR introduction",
    "Complete onboarding paperwork and essential policies",
    "IT setup: device, accounts, and required software",
    "Meet the manager and immediate team"
  ]
}
```
The 5-day template (titles + meeting lists) is a hardcoded constant (`FIRST_WEEK_SCHEDULE`) mirroring `first_week_schedule.md`; it is not read from that file at runtime, so editing the `.md` alone has no effect on the tool's output.

**Weekend handling**: if `start_date` (or any subsequent day while walking the 5-day window) lands on Saturday/Sunday, the tool advances to the next Monday — output dates are always weekdays, but non-consecutive across a weekend.

**Failure mode**: raises `ValueError("Invalid start_date. Please use YYYY-MM-DD format.")` directly on a malformed date — this is the one tool in the repo that raises instead of returning an `"Error: ..."` string (see [Gaps](#gaps--inconsistencies)).

## 4. Onboarding Task Tracker — `tools/tracker_tool.py`

Writes/reads a shared Google Sheet (`SHEET_ID` hardcoded, `Sheet1`, columns `Employee | Role | Task | Status | Owner`) via a service-account credential file (`credentials.json`, gitignored, must be created and shared per `SETUP_GOOGLE_SHEETS.md`). Valid `status` values: `Not Started`, `In Progress`, `Completed`, `Blocked` (case-sensitive).

### `@tool log_status(employee: str, role: str, task: str, status: str, owner: str) -> str`
**Input**: all 5 fields required, non-blank; `status` must be one of the 4 valid values.
**Output**: `"Logged: <employee> | <task> | <status>"` on success. On failure: `"Setup Error: ..."` (missing `credentials.json`), `"Error: ..."` (bad/missing field, invalid status, sheet/worksheet not found), `"Unexpected error: ..."` (anything else).

### `@tool get_employee_tasks(employee: str) -> str`
**Input**: `employee` name, required.
**Output**: multi-line string listing that employee's `- <task> [<status>] (Owner: <owner>)` rows, `"No tasks found for <employee>"` if none, or an `"Error: ..."`/`"Unexpected error: ..."` string on failure.

### `@tool update_task_status(employee: str, task_name: str, new_status: str) -> str`
**Input**: all 3 fields required; `new_status` must be one of the 4 valid values. Matches by exact (case-insensitive) employee + task text.
**Output**: `"Updated <employee>'s '<task>' to <status>"`, or `"Task not found for <employee>: <task>"` if no row matches, or an error string.

### `@tool get_all_tasks() -> str`
**Input**: none.
**Output**: a formatted plain-text table of every row in the sheet (`"OnboardOps Tracker - All Tasks"` header + numbered entries), `"No tasks logged yet."` if the sheet is empty, or an error string.

**Verified behavior**: `test_tracker.py` unit-tests all 4 functions against a mocked `gspread` client (no live credentials needed); `test_tracker.py --live` and `test_tracker_integration.py` exercise them against the real sheet, including a 4-scenario simulation of the checklist/scheduling/IT/HR tools all feeding the same tracker row-by-row.

## 5. Orchestrator — `agent.py`

**Input**: a single natural-language prompt string handed to `agent(prompt)`, e.g.:
> "A new hire named Rajesh Kumar is joining as a Software Engineer in Engineering, starting 2026-09-08. Please generate his onboarding checklist, tell him how many paid leave days he gets, create his first-week schedule, and log that his 'Laptop provisioned' task is In Progress, owned by IT."

**Output**: the Strands `Agent`'s natural-language response, after it has decided (via tool-calling) which of the wired tools to invoke and folded their string/list outputs back into a conversational reply.

**Currently wired tools** (7 of the 8 available tool functions in the repo, as of 2026-09-06):
```python
Agent(tools=[
    answer_hr_question,
    generate_checklist,
    generate_schedule,
    log_status,
    get_employee_tasks,
    update_task_status,
    get_all_tasks,
])
```
`answer_hr_question` here comes from `tools/hr_qa_wrapper.py` (the relative-path-dependent instance, not the `PROJECT_ROOT`-based one in `tools/hr_qa_tool.py`). Only `list_hr_policy_categories` remains implemented and tested independently but not exposed to the live agent.

**Note**: `agent.py`'s own embedded test prompt (run on import) currently exercises only the query tools (`"What tasks does Rajesh Kumar have so far?"`) — the original compound scenario (checklist + HR Q&A + schedule + log, all in one turn) that used to live here was moved to `e2e/test_agent_full_integration.py` (Scenario A) once the query tools were added, so that specific cross-tool path stays covered by an automated test rather than only by `agent.py`'s own ad hoc script.

## Gaps & inconsistencies

Worth resolving, found while documenting the above — none block current functionality, but they're sources of confusion:

1. **Duplicate `answer_hr_question`**: `tools/hr_qa_tool.py` and `tools/hr_qa_wrapper.py` each define one, with different singleton lifetimes and path resolution (`PROJECT_ROOT`-based vs. CWD-relative). `agent.py` uses the wrapper's version; `tools/__init__.py` exports the other. Pick one.
2. **Inconsistent error convention**: `generate_checklist`, `answer_hr_question`, and all 4 tracker functions catch exceptions and return `"Error: ..."`/`"Unexpected error: ..."` strings; `generate_schedule` raises `ValueError` directly. A caller (or the agent's tool loop) handles these two failure modes differently.
3. **Orchestrator wires 7 of 8 tool functions** — only `list_hr_policy_categories` is implemented and tested but not reachable through `agent.py`. *(Resolved 2026-09-06 for the other 3 — `get_employee_tasks`, `update_task_status`, `get_all_tasks` are now wired.)*
4. **`sample_output.json` is not live output** — it documents a task schema no current tool produces; useful as a future-direction reference but easy to mistake for actual behavior.
5. **No client-side timeout on `generate_checklist`** — a single Bedrock call has been observed taking >3 minutes under load; nothing currently caps this.
6. **Checklist items are a poor fit for tracker Task values, and can't be reliably re-referenced across generations** — see `KNOWN_ISSUES.md` #3 for the full detail. Partially mitigated 2026-09-06 (`short_task_label()` + updated tool docstrings), but the underlying non-determinism + exact-match-only lookup limitation remains open; a real fix needs task IDs in the tracker sheet.
